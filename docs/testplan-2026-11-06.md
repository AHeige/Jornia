# Wisp test plan for 6 November 2026

## Working method

Take **one experiment at a time**, in the order below. Record results/uncertainty before the next experiment. This is a plan with later progress entries, not a claim that every planned test ran. All experimental/product logic is first-party under `AGENTS.md`.

Goal: Cone Thrower asks what to do next inside WoW and receives help grounded in current context, without reload or alt-tab.

## 1. Fast outbound game data

**Status: completed.** See [measurements/limits](chatlog-test-2026-11-06.md). Eight messages arrived in game but appeared on disk only when the full client exited. Immediate off/on and a nominal 250 ms gap did not flush quickly.

Send one uniquely marked self-whisper and measure disk arrival:

- A: ordinary chat logging with no extra action.
- B: disable/re-enable logging after in-game receipt.

Immediate B flushing is a **hypothesis**, not established behavior. [BabelChat reports long buffering](https://github.com/Yumash/BabelChat#how-it-works); that is background, not our Mac/build measurement.

Self-whispers pass through the server and native logging may save unrelated chat locally. Process only our unique markers; send no chat to AI. Preserve/restore logging settings, without changing/deleting existing logs.

Record ID, build, character, A/B variant, send time, game receipt, first disk observation and toggling. Use common clocks or disclose offsets; distinguish game latency from poll interval. Use fresh IDs and repeated trials. No reload/logout in the measurement interval. If unseen, report elapsed waiting and not observed, never zero latency.

**Decision:** is this fast/repeatable enough for conversation? Report latency, variation, missing messages and limits first.

## 2. Useful snapshot

**Initial status: waiting for test 1 evaluation.**

Capture level, zone, active quests, objectives/progress and the player's question. The journal is long-term memory; the snapshot is dated current state with character ID/freshness. Not every event needs an AI call. Acceptance, progress and turn-in are distinct.

**Verification:** compare against visible WoW state, including level-ups and changed objectives. Check character isolation and prevent stale information being called live.

## 3. Real AI replies in Lua

**Initial status: waiting for test 2 evaluation.**

Connect Berget to the proven file inbox. Two actual no-reload Lua replies establish only a limited return route, not a finished bidirectional AI chat.

Investigate readiness detection before consuming inboxes, conversation capacity and understandable exhaustion handling. Bind replies to character/session/question. AI text is data, never generated Lua code. Retain receipts and protection against uncertain paid replay.

**Verification:** measure question → current context → AI → file → visible reply. Test latency, failures, duplicate replies, character changes and exhaustion. Static replies do not verify inference.

The user chose a dedicated Lua window rather than a normal WoW chat channel, enabling styled replies, sources, context age and relevant follow-ups. This is step-3 direction, not part of the chat-log experiment. The generic `/run` custom-script warning must not appear in normal use.

The user proposed visible OCR after Enter, now ahead of SpeakText. Local OCR on an already attached game image worked in three runs: 7.673/0.210/0.185 seconds, with an extra space in a function name. ### E2E completed

A real Berget answer appeared automatically in the running Lua window: **6.1 s Enter-to-answer**, final OCR 46.2 ms/capture+OCR 212.4 ms. An undersized output limit caused model failure and was fixed; Go/API/model adapter were tested/updated. No reload/logout/exit. Only the question was sent, no journal. Next scope: relevant current context and durable return beyond finite inboxes. See OCR notes for limits.

### Reusable return signal verified

Code research distinguished sound content from file presence. An independent Mac probe observed ten remove/recreate cycles as **20 Lua transitions** on one filename, without further inbox loads/reload/restart. The player was already at character selection; explicit permission allowed entering Cone Thrower. This establishes a reusable boolean, not text transport. Next: checked bytes and OCR acknowledgements, then speed/frame-cost measurement. See `docs/return-channel-research-2026-11-06.md`. Inbox 04 restored exactly; probe auto-stopped after 120 samples. No third-party implementation was adopted.

### Text over the same reusable carriers

`Hi`, `Again` and UTF-8 `åäö` displayed correctly; local OCR read final receipts. Eight data carriers plus clock reused, no inbox consumed per byte/message. Corrupt packets were rejected before display. Short-payload times: 4.61/8.40/7.96 s. Byte acknowledgements are too slow for long replies; next scope is blocks/game cost. See `docs/return-byte-slice-2026-11-06.md`. No reload/logout/restart/network/AI cost. Carriers/bootstrap files restored.

### Block slice completed

Eight bytes per acknowledgement worked in the same running client. New byte reference for Again: 5.33 s; final block version 1.44 s. A 257-byte packet including åäö took 14.98 s. Bad checksums/stale nonces rejected before display. OCR merged numeric fields and WoW's large-digest formatting limit were identified/fixed; failed trials remain documented. FPS showed 60/60/60 in a short stationary trial, no general guarantee. Carriers/bootstrap files restored and ordinary OCR reader restarted. See [block results/limits](return-block-slice-2026-11-06.md). The AI flow had not yet adopted this return at this checkpoint.
