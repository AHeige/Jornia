# Companion mutation contract v1

Scope: the local companion process and its private SQLite database. It is not a cloud account or an event-sourcing framework. This slice introduces one shared browser runtime (`Mutations` in `web/app.js`) and the corresponding SQLite operation journal; no shared runtime existed in this repository before this work.

| Action | Strategy and evidence | Duplicate/concurrency/recovery contract |
| --- | --- | --- |
| Import journal | Acknowledged. Preview identifies the character and event count. Success means one SQLite transaction committed characters/events and its operation receipt. No provisional historical facts are presented. | Same mutation ID/payload returns the saved receipt. Different payload under the same ID conflicts. Events deduplicate by stable ID and canonical content; changed content conflicts atomically. Reimport with a new mutation ID adds no duplicate events. A browser transport failure reads the receipt; it never replays a write automatically. |
| Ask | Acknowledged because retrieval/inference is not locally predictable. The form shows pending feedback immediately, before network completion. Success means the answer and local conversation/operation receipt committed. | Browser single-flight coalesces repeated form submissions. SQLite permits one pending ask per character across tabs. The stable operation is owned by the process beyond the browser request. Lost browser responses recover by receipt lookup. Remote inference is never automatically retried. Unknown remote outcomes are labelled needs-attention. A new deliberate question has a new ID. |
| Forget character | Confirmation-first. The UI describes permanent local deletion and asks the user to confirm. Success means the SQLite deletion transaction committed, including imported events and conversations. | Uses the same mutation runtime and persisted receipt. Active asks block deletion. A completed repeated mutation returns its receipt; repeated deletes have no additional destructive effect. The retained receipt contains no raw character ID, journal or conversation content. |

Operation payload hashes bind identity to content. Request intents are stored locally for recovery. On process restart unfinished operations become needs-attention, rather than being replayed. The process uses one exclusive SQLite connection, preventing a second instance from claiming unfinished operations in the same file. Distinct data directories remain independent. Idempotency receipts are retained until character deletion; the minimal deletion receipt remains locally so a lost deletion response can be reconciled.

The browser shows results from authoritative SQLite reads, not guessed successful business outcomes. Refresh generations reject older reads after a newer refresh starts. Drafts remain in session storage when validation fails, and committed requests are available through local operation state. There is no offline queue for world/model questions, no background personal-data sync, and no automatic paid retry. Personal memory questions work offline.

No provisional reducer, event projector, cross-device revision stream, cloud authorization, or model-side exactly-once guarantee exists or is claimed. These mechanisms are inapplicable to this local acknowledged-result contract. There is still an unknown-outcome boundary if the remote model runs but the server process/transport fails before an answer can be saved; the UI must expose it instead of promising a rollback or free retry.

Verification: Go tests cover duplicate requests, conflicting payloads/events, per-character pending exclusion, restart recovery and no private context in remote request envelopes. Lua 5.1 simulation executes the actual addon and validates its exported packet through the companion parser. Browser tests cover immediate pending state under a delayed transport, five rapid submissions producing one request, rejected requests preserving drafts, lost post-commit responses recovering without replay, repeat import, character isolation, process restart/offline memory, and mobile reflow. Run `make e2e` against the local server with an installed Playwright Chromium. This Mac uses `PLAYWRIGHT_BROWSERS_PATH=/Volumes/Extern/CodexCaches/ms-playwright make e2e`.

## Demo activation (v1)

`demo.activate/v1` uses acknowledged feedback through `Mutations.submit`, with one in-flight activation per browser and the same persisted import receipt contract on the server. The canonical synthetic packet has stable event IDs and a reserved installation identity. A completed receipt proves SQLite committed the import; an authoritative state refresh selects the marked demo character. Repeated activation deduplicates events and preserves conversations. Definitive rejection retains the current character and shows the error beside the action. A lost response is recovered by receipt lookup without replay. Real imports cannot use the reserved identity. Demo labels and source statuses persist after process restart; a different character never receives demo memory. The existing forget action can delete the demo journal after its normal confirmation.

The result is kept visually static to avoid moving the conversation while it is read. Button disabling and inline “Förbereder…” acknowledge activation immediately; no success or demo banner appears before the receipt and state read. Existing daisyUI input feedback is retained, including reduced-motion behavior. The connection check is read-only, sends no question and invokes no model.

## Local journal consent/configuration (v1)

`journal.configure/v1` owns the single local journal configuration. It uses the existing `Mutations.submit('journal', ...)` runtime with acknowledged feedback: folder validation and permission intent must be accepted before reads begin. There is no provisional graph or consent state. The button disables synchronously, while inline text acknowledges the action; a completed receipt proves the revisioned config and receipt committed in one SQLite transaction. A background worker then performs the separately labelled file import; configuration success does not assert that journal files exist or were imported.

Duplicate in-flight form/button/keyboard activation is single-flight. Same mutation ID/payload returns its receipt; mismatched payload conflicts. Distinct intentional enable/pause actions get distinct IDs. Expected config revisions prevent stale tabs from silently overwriting another change. A stale editor keeps its input and is asked to reload saved state. Failed validation preserves the draft and does not start reading. Lost replies use read-only receipt recovery without replay. Reload recovers the saved configuration, and process startup resumes only an enabled, persisted permission. There is no settings offline queue. The selected local directory is never uploaded.

Automatic imports are local, idempotent data ingestion, not paid calls. They use content-derived operation IDs, canonical event IDs and transactional event/graph/receipt commits per packet. Partial/malformed files retain the previous confirmed graph and are checked again later. A concurrent forget operation atomically inserts a hashed per-character import exclusion and cascades graph/event/conversation deletion; future file reads cannot recreate the character. Explicit manual import clears that exclusion. Other characters are unaffected. The background reader is cancelled with the companion process.

Read-only polling reconciles discovered characters and new observations, preserves the selected character and draft, and rejects reads superseded by a newer refresh generation. The journey timeline remains static while read; no scrolling or decorative animation is triggered by file updates. Existing daisyUI input feedback is reused. The mobile chat form stays in normal flow to avoid covering history; desktop retains its existing sticky form. Normal and reduced-motion rendered browser flows are covered.

Verification covers initial unchecked consent, no pre-consent import, initial multi-character discovery, five rapid settings activations producing one POST, a lost committed settings reply, file-change import, pause/resume, process restart with saved permission, character isolation, offline journey answers, mobile reflow, stale-config rejection, executable/partial Lua rejection, large journal chunking, projection rebuild, full history export, and forgotten-character suppression.

The earlier statement that there is no projector applies to the original slice: 0.3.0 adds a local rebuildable SQLite graph projection. There is still no cloud event stream, provisional-history reducer, or automatic remote personal-history sync.

## Personal AI question and tester access (0.4.1)

`ask/v2` retains the existing acknowledged, single-flight receipt runtime and no-replay policy. Optional journal sharing is off by default and scoped to one question. A read-only preview selects up to eight recent non-note observations for the chosen character. The exact displayed set is bound by a digest of character, event identities, content and demo status; POST validates those immutable local observations before accepting the operation. Cross-character and stale/mismatched context are rejected. No provisional answer is shown. Failed requests preserve the draft and consent for review; confirmed requests reset sharing. Character IDs, names, notes and conversations never enter the remote journal envelope. Remote references are request-local `memory:1`, etc.; the companion maps citations to local event links after response.

`access.configure/v1` uses the same acknowledged runtime. A read-only remote health check validates the supplied code before a transaction stores the local setting and completed receipt. The credential is redacted from request journals and omitted from export. Failed validation preserves the input; unknown outcomes use receipt lookup, never automatic replay. Separate intentional code replacements use separate operation IDs; simultaneous code edits across tabs have last-committed-write semantics rather than a revisioned editor. The runtime uses an atomic token value for concurrent reads. Access does not alter journal permissions.

The shared daisyUI input feedback is retained; result/history/preview remain static for reading and reduced motion. The form now stays in normal flow on desktop too: the enlarged context preview must never cover an answer. Verification: `personal.mjs` covers explicit sharing, no implicit sharing, exact preview, synthetic labels, five clicks/one POST, lost post-commit reply recovery, per-question reset, credential-free export, mobile overflow and reduced motion. Go/SQL tests cover cross-character context rejection, unsupported journal fields, fabricated evidence IDs, authentication, quota, revocation and persistent duplicate request rejection. The packaged Mac client was additionally exercised through the production HTTPS endpoint and the actual LangChain/Berget model using synthetic journal data.

## Character discovery and Armory (0.5.0)

The first-use configuration remains acknowledged through the same `Mutations` runtime. Consent version 2 explicitly includes character-directory names and Wisp journals; existing version-1 consent continues only its previous Wisp-journal reading and does not silently expand. Conventional installation paths (and Windows registry install paths) can be detected without reading characters. Directory discovery begins only after saved consent. It is bounded, ignores symlinks and reads no other addon/config contents. Directory identity has no inferred level, gear or journey. In 0.5.2, directory rows are preliminary. A bounded data-only `WispCharacterDB` marker in Wisp’s per-character SavedVariables binds the exact directory to installation ID + GUID before importing the account journal. Name/realm guessing was removed. An unclaimed preliminary ID stays stable. If the journal arrived first, only an empty preliminary row can be retired; independent content is preserved. Reused folders with a different GUID cannot overwrite the previous journey. Alias and folder identities are included in forget exclusions to prevent resurrection.

`profile` is acknowledged, with a global browser single-flight and a persisted per-character pending exclusion across tabs. The request contains an explicitly approved public full name and region. Same mutation ID/payload returns the saved receipt; conflict is rejected. No provisional portrait or equipment is shown. The gateway validates tester access, accounts for a server request and prevents remote request-ID replay. A lost browser reply reads the local receipt rather than issuing another lookup. Failure preserves the existing journal/profile and input; confirmed success selects the resulting character and clears lookup consent. Matching names are checked before attaching to an existing character, with a separate Add-character choice.

The personal snapshot is local, source-scoped to Forever, dated and expires within 28 days. Server profile data is not persisted in world knowledge. Browser images may load only from the explicit Blizzard render host under the existing CSP. Equipment/media identity must match the requested profile. A missing optional gear or media endpoint yields a partial snapshot with a warning; identity/namespace mismatches fail. Expiry removes only API-derived profile data, never journal entries. Export includes unexpired profiles, excludes credentials, and delete cascades profile storage. Incoming older snapshots cannot overwrite newer expiry/fetch generations. Existing avatar/landscape art is static; no decorative motion or polling-triggered animation.
